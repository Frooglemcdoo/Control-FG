# R153 — native lighting accumulation capture

R152 upload: all seven archive hashes and every chunk hash verified. Four complete frames from PID 42920: 3546/3547 (visible), 4819/4820 (faded). Each pair has consecutive frames, successful RR result 1, Model F (6), no reset on the recorded frame, 2560x1440 input and 3840x2160 output. Input and output RGB contain no nonfinite values. All 48 resource files match metadata dimensions and byte counts.

The broad floor-shadow change is visible in pre-RR color as well as RR output. Common 640x360 area reductions show median output/input luminance ratios about 0.993–0.994 in all four frames. This does not prove local equivalence: edges, camera changes and different sample grids prevent a pixel-for-pixel comparison. The camera moved between positions; full-image brightness averages do not identify a cause. The captures contain raw GI and albedo guides, but not the accumulated diffuse/specular lighting buffers.

Both requests were queued while RR was suspended and consumed shortly after gameplay resumed. The probe records frame_without_lighting pauses and native-menu handshakes; this is not evidence that the user toggled the RR setting. Frame 4815 logs RR selected again, followed by captured frames 4819/4820; both pairs follow a native history reset. Therefore the upload does not establish settled RR behavior. Do not conclude RR is globally fault-free or attribute the remaining change to exposure.

R153 waits for three seconds of consecutive evaluated gameplay frames after a request before preparing the pair; history resets, missing reset metadata, frame gaps and failed evaluations restart settling. This is a nonblocking timestamp gate, not a sleep or GPU wait. The overlay explains that the user should return to gameplay and hold still.

R153 extends the same button-driven pair capture with native `lighting-diffuse` and `lighting-specular` resources, using the existing renderer ShaderTexture offsets. Both are copied before RR on the original command list alongside color, GI and guides. They represent accumulated lighting at this boundary, not isolated direct-light deltas or final tone-mapped pixels. Existing `diffuse` and `specular` filenames remain RR material guides; they must not be mistaken for lighting.

Both extra resources require native wrapper state validation, a matching device, supported single-mip full-resolution formats, unique resource identity, ordered nonblocking state locks, and revalidation under those locks. No writable state is guessed. Failure is visible and diagnostic logs can still be packaged. Resource/barrier capacity and native-lock capacity now use shared constants. Worker allocation/export and existing fence polling remain; there is no new render-thread wait or file write. Two RGBA16F buffers at 2560x1440 add about 112.5 MiB of readback allocation across the two prepared slots and 225 MiB of raw data across four frames; ZIPs remain below 200 MB each.

Test: install with Control closed, start a fresh session, select Default and enable RR. Leave RR enabled for both positions. Click Capture RR at the first position, return to gameplay if a game menu is open, and hold still until Saved pairs: 1/2. Move to where the shadow fades, capture again, and wait for 2/2. Click Package RR and send all ZIPs. If unavailable/failed, Package RR preserves diagnostics. No capture hotkeys or beeps are required.

Rendering/shadow shaders, authored clipping, corrected surface normals, centered softness, current-frame spot visibility, native point history, GI filtering, Model F/60%, skin/glass and exposure are unchanged. This is a targeted diagnostic build, not a claimed shadow fix. Windows build/WARP validation cannot establish in-game buffer availability or RTX behavior.
